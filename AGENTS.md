# AGENTS.md

Guidance for AI agents and contributors working on **Guitarists**, a cross-platform desktop app for expert guitarists.

## Project Overview

Guitarists is a native desktop application written in **Go** using **Wails v3**. It targets Windows, macOS, and Linux. The Go backend owns all business logic, platform integration, and file I/O; the web frontend is rendered in the platform webview and communicates with Go through Wails services.

The app must remain lightweight (no bundled Chromium), offline-first, and store user data locally.

## Features

### 1. Guitar Tuner
- Capture guitar string audio from the microphone.
- Detect the pitch of the incoming signal and compare it to the expected note for the selected string.
- Show real-time feedback: detected note/frequency, cents deviation, and a clear "in tune" / "sharp" / "flat" indication.
- Support standard tuning (E2 A2 D3 G3 B3 E4) with the ability to select a target string or auto-detect.

### 2. Metronome
- Configurable BPM, time signature, and subdivisions.
- Accent the first beat of each measure.
- Audible click (and optional visual beat indicator) with low-latency timing.
- Play/stop controls, tap tempo, and tempo adjustment while running.

### 3. Songs
- Save songs as **tab only**, **chords only**, or **tab + chords**, chosen when a new song is created.
- Tab lines show six guitar strings across one or more lyric-labelled staves. Click a string position and press a number key (`0`-`24`) to enter a fret; support rests, deletions, cursor navigation, and cloning a line.
- Press `/` on an existing note and then a fret number to enter a slide (rendered `fret/slideTo`); press `/` again to remove the slide.
- Configure an optional pause (in beats) after each tab line. Tab moves from lyrics into the staff; Tab/Shift+Tab from the staff moves to the next/previous line's lyrics, adding a line when needed.
- Chord lines pair lyrics with a chord or short chord progression. Chord-only and mixed songs expose a strumming pattern above all lines.
- Mixed songs provide separate buttons to add tab lines or chord lines; every line records whether it is a tab line or a chord line.
- Preview playback at the song tempo for tab lines, using the standard tuning frequencies; highlight notes as they play for both full-song and single-line playback. Chord lines are skipped during playback.
- Store songs locally as **XML** files under the platform's Documents directory:
  - Windows: `C:\Users\<user>\Documents\guitarists-tabs`
  - Linux/macOS: `$XDG_DOCUMENTS_DIR` (or `$HOME/Documents`) `/guitarists-tabs`
- Load existing XML song files back into the editor.
- Save/load must be resilient to malformed or missing files and must never write outside the songs directory.

## Tech Stack

- **Backend:** Go (latest stable), Wails v3 (`github.com/wailsapp/wails/v3`).
- **Frontend:** Vite + TypeScript web app under `frontend/`, embedded via `//go:embed all:frontend/dist`.
- **Build orchestration:** `Taskfile.yml` (go-task), generated by the Wails v3 toolchain.
- **Persistence:** XML files on the local filesystem for songs. No remote services, no telemetry.
- **Audio:** Go audio/microphone capture and pitch detection. Keep platform-specific audio code isolated behind build tags in its own package.

### Architectural Rules

- **Thin service adapters:** Wails services in `internal/services/` only translate frontend calls into domain operations. Real logic lives in Wails-free packages (`internal/tuner`, `internal/metronome`, `internal/tabs`) so it can be unit tested with plain `go test`.
- **No Wails imports in domain packages.** Only `internal/services` and `main.go` may depend on the Wails framework.
- **Input validation:** Treat all frontend input as untrusted. Validate numbers, strings, filenames, and paths in service methods before use.
- **No path traversal:** Never join raw frontend-supplied names into filesystem paths. Resolve a safe base directory and validate the final path stays within it.
- **Concurrency:** Services are singletons shared by all windows. Protect mutable state with `sync.RWMutex` (or channels for audio pipelines).
- **UI responsiveness:** Long-running work (audio capture, pitch analysis, file scanning) must not block the JS promise. Use goroutines and report state/progress via `app.Event.Emit`.
- **Errors:** Bound methods must return errors; Wails maps them to rejected JavaScript promises. Return actionable error messages, never panic across the boundary.

## Coding Standards

### Go
- Follow idiomatic Go and `gofmt`/`goimports`. Run `go vet` and `golangci-lint` (if configured) before finishing.
- Use the standard library first; add dependencies only with clear justification.
- Return wrapped errors with context: `fmt.Errorf("loading tab %q: %w", name, err)`.
- Pass `context.Context` into blocking/long-lived operations and honor cancellation.
- Keep exported APIs small and documented; prefer unexported types internally.
- Write table-driven tests for pitch detection, tempo math, XML round-tripping, and path resolution. Use `t.TempDir()` for file tests.
- Use build tags (`//go:build windows`, `//go:build linux || darwin`) for platform-specific code; keep the shared interface in a non-tagged file.
- Never log secrets or user audio data; do not write audio samples to disk unless explicitly required.

### Frontend / TypeScript
- Use TypeScript strict mode; avoid `any` (prefer `unknown` plus narrowing).
- Import Wails bindings from `frontend/bindings/...`; never hand-edit generated files. Until bindings are generated, route calls through the typed wrapper in `frontend/src/lib/api.ts` (`Call.ByName`) and keep it in sync with the Go services.
- Keep views focused on presentation/input; delegate domain behavior to Go services.
- Follow the existing component/style conventions before introducing new libraries or patterns.
- Handle rejected promises from service calls and surface clear, non-technical errors to the user.
- Ensure keyboard accessibility for the song editor and metronome controls.

### General
- Match the style of surrounding code. Do not add comments unless they explain non-obvious intent.
- Prefer small, focused commits. Do not commit generated artifacts (`frontend/dist`, build outputs) or secrets.
- Keep everything offline-first. Do not add network calls, analytics, or auto-update mechanisms without explicit approval.

## Song XML Format

Songs are stored as XML. The schema must round-trip losslessly through `internal/tabs`.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<tab version="3">
  <title>Song Title</title>
  <artist>Artist</artist>
  <tuning>E2 A2 D3 G3 B3 E4</tuning>
  <tempo>120</tempo>
  <type>mixed</type>
  <strumming>D DU UDU</strumming>
  <line type="chord">
    <lyrics>First line of the verse</lyrics>
    <chord>G A</chord>
  </line>
  <line type="tab">
    <lyrics>Guitar riff</lyrics>
    <pause>1</pause>
    <measure>
      <beat string="1" fret="0"/>
      <beat string="2" fret="3" slideTo="5"/>
    </measure>
  </line>
  <line type="chord">
    <lyrics>Second line of the verse</lyrics>
    <chord>Em</chord>
  </line>
</tab>
```

- `type` is `tab`, `chord`, or `mixed` and describes the whole song. `tab` stores six-string staves, `chord` stores lyrics with chords, and `mixed` combines both.
- `line` groups one song line; its `type` attribute is `tab` or `chord`. Add more lines for separate song phrases.
- `lyrics` is optional free text shown above its staff or chord.
- `chord` is an optional chord or short progression shown on chord lines (for example `G`, `Em`, `Bsus2`, or `G A Em`).
- `strumming` is an optional pattern shown at the top of chord and mixed songs (for example `D DU UDU`).
- `pause` is optional whole-beat silence after a tab line during playback (0-16, default 0).
- `slideTo` is an optional destination fret (0-24); the note is written as `fret/slideTo` and played as a slide.
- Version 1 files with direct `<measure>` children are migrated into a single tab line; version 1 and 2 files without a song type default to `tab` and save as version 3.
- `string` is 1-6 (1 = high E, 6 = low E).
- `fret` is 0-24; `slideTo`, when present, is also 0-24.
- Preserve unknown elements/attributes when loading and re-saving where feasible.
- Treat missing optional fields as zero values; reject invalid fret/string values and song types with a descriptive error.
- Never silently overwrite a file on load failure; report the error to the UI.

## Build & Development Commands

Use the Wails v3 CLI and Taskfile. Verify exact task names against `Taskfile.yml` once scaffolding exists.

```bash
wails3 dev -config ./build/config.yml   # run app with hot reload
wails3 build                            # build production binary
go test ./...                           # run Go tests
go vet ./...                            # static analysis
```

Install the CLI with `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.34`.
Frontend commands are run from `frontend/` (e.g. `npm install`, `npm run build`).

Linux requires the GTK4 and WebKitGTK 6.0 development packages (`gtk4`, `webkitgtk-6.0`) to link the desktop binary.

Before finishing any change:
1. `gofmt -w` changed Go files.
2. `go vet ./...` and `go test ./...` pass.
3. Frontend type-checks/builds if frontend code changed.
4. No generated or build artifacts are staged.
